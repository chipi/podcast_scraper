# Player performance scan — 2026-10-08

Tool: `make perf-android` (`web/learning-player/scripts/perf/device-scan.mjs`). It attaches to the
app's WebView on the attached device or emulator and walks every main screen. Per screen it reports
time to data, API calls, media, long tasks at a CPU slowdown, JS heap, decoded images, layers,
tile/GPU memory and the app's PSS, as `.test_outputs/perf/android-<ts>/report.md` and `.json`.

**API timing is measured in the page.** `CapacitorHttp` sends fetch through the native stack, so
DevTools never sees API calls. The scan wraps the app's `fetch` instead. A first version reported
artwork and analytics requests as API traffic; that was wrong.

## iOS memory — `make perf-ios` (separate from Android, as asked)

iOS has no DevTools protocol into a WKWebView, so the number comes from outside. `MemoryWalkTests`
walks the installed app by deep link; at each step, `ios-memory-walk.sh` reads `phys_footprint`
(what jetsam counts) of the simulator's WebKit content process and of the app process. iPhone 17
simulator, iOS 26.3, both builds against prod, same account, clean install each:

| step | 1.0.2 content | branch content | 1.0.2 app | branch app |
| --- | --- | --- | --- | --- |
| home | 113 MB | 103 MB | 73 MB | 75 MB |
| episode | 122 MB | 117 MB | 77 MB | 80 MB |
| episode + notes | 139 MB | 129 MB | 77 MB | 80 MB |
| topic | 143 MB | 136 MB | 77 MB | 81 MB |
| person | 148 MB | 141 MB | 77 MB | 79 MB |
| storyline | 158 MB | 147 MB | 80 MB | 83 MB |
| episode again | 154 MB | 146 MB | 81 MB | 83 MB |

The branch's content process is 5–10 MB lower at every step; the app process does not change.

**What this does NOT show yet:**

- **The artwork change.** Prod still serves originals until the deploy, so both builds decode the same
  images. Re-run both walks after the deploy.
- **GPU memory.** The simulator renders with the Mac's GPU, so compositing and tile memory — where
  the blur removal saved most on Android — are not in `phys_footprint`.
- **A real iPhone.** These are simulator numbers only.

## After paging — local stack, fixture corpus (2026-10-08, evening)

Both walks ran against the LOCAL contact-sheet stack (the v3 fixture corpus, the seeded `simtest`
account), after the paging work (`/favorites`, `/highlights`, `/notes`, `/resurfacing`,
`/playback`, `/collections/{id}`, `/podcasts`, `/episodes/batch`). The corpus is small, so these
numbers are NOT comparable with the prod scan above; they show the walk is clean, not how prod
performs. Prod re-measures are in the handover (post-deploy).

`make perf-android` (Pixel 8 emulator, CPU throttle 4×, `.test_outputs/perf/android-local-after-paging`):
every screen settles in under 370 ms (episode 366 ms, everything else under 200 ms), decoded images
at most 15 MB (Home), at most 13 layers.

`make perf-ios` (iPhone 17 simulator, `.test_outputs/perf/ios-local-after-paging`), WebKit content
process footprint: Home 88 MB → episode 100 → notes 106 → topic 115 → storyline 117 → person 115 MB.
It levels off rather than climbing; the app process holds at 73 MB.
