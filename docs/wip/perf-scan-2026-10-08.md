# Player performance scan — 2026-10-08

Tool: `make perf-android` (`web/learning-player/scripts/perf/device-scan.mjs`). It attaches to the
app's WebView on the attached device or emulator and walks every main screen. Per screen it reports
time to data, API calls, media, long tasks at a CPU slowdown, JS heap, decoded images, layers,
tile/GPU memory and the app's PSS, as `.test_outputs/perf/android-<ts>/report.md` and `.json`.

**API timing is measured in the page.** `CapacitorHttp` sends fetch through the native stack, so
DevTools never sees API calls. The scan wraps the app's `fetch` instead. A first version reported
artwork and analytics requests as API traffic; that was wrong.

## Baseline: Pixel_8 AVD, 4× CPU slowdown, this branch's app against prod (`sha-0f63257`)

| Finding | Measured | Fix |
|---|---|---|
| `/your-week` | 3.0–3.3 s on the server (curl, 3 runs); 7.3 s seen in-app on Home | `f5ab549a9` (cached catalog) is on this branch, **not deployed** — re-measure after deploy |
| `/episodes/{slug}/related` | 2.4–3.2 s on the server, every Episode open | cached per (corpus, episode, top_k), 1 h TTL, 512 entries; errors are not cached |
| `/trending` (corpus scope) | ~0.6 s each, ×4 at once on Profile → Interests | cached until the corpus changes or 5 min pass (`perf_cache`); per-user "Mine" stays live |
| `/podcasts` (~80 KB) | fetched 3× on Library → Following, by 7 surfaces in all | one shared request, kept 60 s; a failure is not kept |
| Queue: 247 MB of decoded images | originals in cards (detail artwork) | the artwork change in this PR; effective after deploy |
| Topic card `/topics/{id}` | 286 KB: every episode, sliced to 5 in the client | server-side paging (next item) |
| Long tasks | ≤ 1 per screen, longest 112 ms (Episode) | none needed |

## Not covered by this scan

- Real devices: emulator only.
- iOS: no CDP. iOS memory is a separate item.
- Server numbers after the deploy (`/your-week`, and the caches' hit rates).
