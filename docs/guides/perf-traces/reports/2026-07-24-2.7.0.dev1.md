### The three latency regimes of a search (measured)

`results-paint` above is the **first query on a freshly-loaded page** — the
harness opens a new browser context per run, so every "warm" run is a
first-query. That is the honest "user opens Search and types a query" number.
Breaking it down (submit → first card):

| Regime | total (post-fix) | was (pre-fix) | when |
| --- | --- | --- | --- |
| **process-cold** | ~4.8–6.8 s | (same) | first query after the api boots (index + model load) — #1276 |
| **first-query-per-page** | **~285 ms** | ~788 ms | first query after each page load — the headline above |
| **same-page repeat** | ~115 ms | ~115 ms | 2nd+ query without navigating away |

Server compute for a search is only **~108 ms**. The pre-fix first-query
inflation to ~570 ms server ttfb was **not** search cost — the first query queued
behind `/api/corpus/digest`, which ran ~520 ms of LanceDB **topic-band searches**
(one hybrid search per configured topic) synchronously on the single-worker event
loop. **Fix (landed this session):**

1. `search_corpus` / `search_compare` run their native work off the event loop via
   `run_in_threadpool`, behind a process-wide single-flight semaphore
   (`_LANCE_GATE`) — the loop is freed without allowing concurrent native LanceDB
   reads (#1205-safe).
2. `/api/corpus/digest` **caches its topic bands per process**, keyed on
   `(corpus, window, since-day, band-config)` and stamped with the lance-index
   mtime — so a warm page-load does **zero** band searches and self-invalidates
   on reindex (mirrors `search.index_pool`).

Net measured: **788 → 285 ms**. The residual ~170 ms over the same-page-repeat
(~115 ms) is the remaining page-load fan-out (`/api/corpus/feeds`,
`/api/index/stats`) still on the loop — a smaller, optional follow-up. Process-cold
(#1276) is untouched.

## Common-sense assessment — what's off vs where we'd want to be

**First-query-per-page is now fixed (788 → 285 ms). Two cold paths remain, both accepted/tracked.**

1. **Search first-query-per-page — FIXED this session: 788 → 285 ms** (−64%,
   measured median-of-6). Root cause was `/api/corpus/digest`'s ~520 ms of
   LanceDB band searches hogging the single event loop; fixed by (a) running
   search/compare off the loop behind a single-flight gate (#1205-safe) and
   (b) per-process digest topic-band caching (self-invalidates on reindex). The
   residual ~170 ms (vs ~115 ms same-page-repeat) is `/api/corpus/feeds` +
   `/api/index/stats` still on the loop — optional follow-up.

2. **Search process-cold — ~4.8–6.8 s (first query per process).** Accepted this
   release; tracked in **#1276** (`performance`). Index-open + embedding-model
   load; fix is a startup warmup.

3. **Graph time-to-canvas — ~5.8 s (from the [graph-v3 report](graph-v3-tuning-2026-07-19.md), not re-captured this run).**
   The sibling cold experience, client-side (fcose + KG-second-wave full rebuild).
   Want: < ~2 s. Known; the real fix is the incremental-append refactor
   (`cy.add(delta)` instead of destroy+rebuild) tracked in **#1219**
   (`performance`). Accepted this release.

4. **operator-compare — ~800 ms (steady, no cold gap).** Two subject-scoped
   searches + two `build_briefing_pack` passes, run serially. Tolerable for an
   explicit heavy action; if it grows, parallelize the two sides (independent).
   Low priority.

5. **Everything else is where we'd want it** — filter-apply ~28 ms, cmdk-open
   ~2 ms, operator-cluster ~15 ms, all three surfaces < 30 ms. No action.

**Bottom line:** first-query-per-page is fixed (**788 → 285 ms**). Search *compute*
is ~108 ms, repeats ~115 ms. What remains is two **cold** paths — search
process-cold ~5–7 s (#1276 startup warmup) and graph time-to-canvas ~5.8 s (#1219
client-side rebuild) — both accepted for 2.7.0.dev1. `operator-compare` ~800 ms is
the only steady-state item worth a later look.
