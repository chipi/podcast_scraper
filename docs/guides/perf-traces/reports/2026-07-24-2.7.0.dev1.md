### The three latency regimes of a search (measured)

`results-paint` above is the **first query on a freshly-loaded page** — the
harness opens a new browser context per run, so every "warm" run is a
first-query. That is the honest "user opens Search and types a query" number.
Breaking it down (submit → first card):

| Regime | total | server ttfb | render | when |
| --- | --- | --- | --- | --- |
| **process-cold** | ~4.8–6.8 s | (dominant) | ~15 ms | first query after the api boots (index + model load) |
| **first-query-per-page** | **~788 ms** | ~570 ms | ~5–15 ms | first query after each page load — the headline above |
| **same-page repeat** | ~115 ms | ~108 ms | ~5 ms | 2nd+ query without navigating away |

Server compute for a search is only **~108 ms**. The first-query-per-page
inflation to ~570 ms **server ttfb** is not search cost — it is **event-loop
head-of-line blocking**: `search_corpus` is `async def` but runs
`structured_corpus_search` (embed + BM25 + vector + RRF, ~108 ms CPU)
**synchronously on the single uvicorn worker's event loop**, and the page-load
request burst (`/api/health`, `/api/artifacts`, `/api/corpus/*`,
`/api/app/preferences`) serializes with it. Once the burst drains, repeats are
~115 ms. **Fix:** offload the blocking search to a threadpool
(`run_in_threadpool`) — tracked in #1276.

## Common-sense assessment — what's off vs where we'd want to be

**The search first-query path is the one thing off; everything else is snappy (repeats ~115 ms, surfaces <30 ms).**

> **Decision (2026-07-24):** the search first-query cost and the graph
> time-to-canvas below are **accepted for 2.7.0.dev1** — a conscious trade-off
> this release, not unaddressed regressions. Recorded so the next reader knows
> they were seen and deferred, tracked (#1276, #1219), not missed.

1. **Search first query — ~788 ms per page (and ~5–7 s process-cold).**
   (Accepted this release; tracked in **#1276**, `performance`.) Two distinct
   costs, both on the *first* query, neither is search compute (~108 ms):
   - **Process-cold (~4.8–6.8 s):** first query after the api boots pays
     LanceDB index-open + embedding-model load. Fix: warm at startup.
   - **First-query-per-page (~788 ms):** `search_corpus` is `async def` running
     ~108 ms of CPU **synchronously on the single-worker event loop**, so it
     serializes behind the page-load request burst. Fix: `run_in_threadpool`.
   Steady repeats are ~115 ms. Want first-query < ~300 ms; both fixes are small
   and self-contained.

2. **Graph time-to-canvas — ~5.8 s (from the [graph-v3 report](graph-v3-tuning-2026-07-19.md), not re-captured this run).**
   The sibling cold experience, client-side (fcose + KG-second-wave full rebuild).
   Want: < ~2 s. Known; the real fix is the incremental-append refactor
   (`cy.add(delta)` instead of destroy+rebuild) tracked in **#1219**
   (`performance`). Accepted this release.

3. **operator-compare — ~800 ms (steady, no cold gap).** Two subject-scoped
   searches + two `build_briefing_pack` passes, run serially. Tolerable for an
   explicit heavy action; if it grows, parallelize the two sides (independent).
   Low priority.

4. **Everything else is where we'd want it** — filter-apply ~16 ms, cmdk-open
   ~2 ms, operator-cluster ~16 ms, all three surfaces < 30 ms. No action.

**Bottom line:** search *compute* is ~108 ms and repeats are ~115 ms — the app is
fast once going. The perf story is **the first query**: ~788 ms per page
(event-loop contention → threadpool fix, #1276) and ~5–7 s per process
(index+model cold → startup warmup, #1276), plus **graph time-to-canvas ~5.8 s**
(#1219, client-side rebuild). `operator-compare` ~800 ms is the only
non-first-query item worth a later look.
